PROBLEM
───────
1. Double save: the Submit button (btnSubmit) stays active while the
   form is saving. A double-click can create two identical rows in SharePoint.
2. Same day twice: nothing stops an employee from logging the same Work
   Date twice. Every save creates a new row, because the form is always in
   New mode (DefaultMode: FormMode.New, Item: Defaults('Daily PNQ Log')).


WHAT CHANGES
────────────
- A new variable, _isSaving, disables the Submit button and changes its
  text to "Saving..." from the moment the employee presses Submit until
  SharePoint answers.
- Before saving, the app looks for a row created by the same person for
  the same Work Date. If one exists, it shows a warning and does not save.
  The employee can still edit that row in the SharePoint list (the
  SharePoint List button), as today.
- If the duplicate lookup itself fails (for example the network drops),
  the app does not block the employee. It goes on to save, as it does
  today.

Unchanged
- The target of 8, the exempt reasons, the reason and recovery messages,
  and the required fields.
- All SharePoint columns and DataField/Update bindings.
- The success and error messages.


CORRECTION TO EARLIER ADVICE
────────────────────────────
Earlier I said the Recovery Date picker defaults to today, so the recovery
check could not trigger. That was wrong. The full control definition
(Controls/4.json) shows dpRecoveryDate.SelectedDate is empty, so the picker
already starts blank and the recovery check works.

The card's Default: Today() is not read by anything. It is harmless, so
this record does not change it.


IMPACT ANALYSIS
───────────────
- Duplicate lookup, delegation: it uses the SharePoint columns Created By
  (Author) and Work Date (WorkDate, date only). Both support equality
  filters, so SharePoint does the search. It checks the whole list, not
  only the first 500 rows. It returns only the ID, so it adds one small
  query per save.
- Duplicate lookup, list size: once a SharePoint list has more than
  5,000 items, SharePoint rejects filters on columns that are not indexed.
  The lookup then fails, IfError lets the save through, and duplicates are
  no longer blocked (no error is shown). Index both columns (step 0 below)
  to prevent this.
- Duplicate lookup, which rows it catches:
  - It compares User().Email with the Created By email. In most tenants
    these match. If they don't, the check never finds a duplicate, which
    is the same as today.
  - Rows created by another person, or directly in SharePoint by another
    account, are not detected.
- _isSaving is set back to false in each of these cases:
  - Form.OnSuccess (saved)
  - Form.OnFailure (SharePoint rejected the save)
  - Form.OnReset (new; this runs on ResetForm, so the Clear button
    unlocks Submit too)
  - a duplicate was found
  - closing and reopening the app
- Visual: while busy, Submit shows "Saving..." in the classic button's
  default disabled (greyed) colours.
- Classic buttons already grey out briefly while their OnSelect runs.
  That covers the duplicate lookup but not the save itself, so _isSaving
  is still needed.
- Links: the SharePoint List button opens the "Daily PNQ Log Prod" list. Confirm
  that is the same list the dev app writes to, so testers look in the right
  place.


EXACT IMPLEMENTATION STEPS
──────────────────────────
Grouped by control. Do A1 first, because it creates the _isSaving variable
that the other items use. Paste formulas without an initial equals sign.

0. SharePoint (dev and prod lists): open the list > Settings (gear) > List
   settings > Indexed columns > Create a new index. Create one index on
   Work Date and one on Created By. This is a list setting, not an app
   change, and it does not change any data.

TESTING IN DEV
──────────────
Before you start: in the dev SharePoint list, delete (or note) any rows you
created for today and for the two test dates you plan to use.

Primary
1. Today's Work Date, enter 8 + 0, press Submit. Expected: success message,
   form resets, one new row in the dev list.
2. Without changing the date, enter 8 + 0 again and press Submit.
   Expected: warning "You already have an entry for <today>..." and no new
   row. Submit is active again right after the warning. If no
   warning appears, use the Fallback under A1.
3. Change Work Date to a day you have not logged, enter 8 + 0, and click
   Submit quickly two or three times. Expected: Submit greys out and shows
   "Saving..." after the first click, and only one row is created.
4. Pick the date from test 3 again and press Submit. Expected: the duplicate
   warning. If no warning appears although the row exists, use the
   Fallback under A1.

Regression
5. Total below 8 with no reason: "please select a reason" message, no row,
   Submit stays active.
6. Total below 8, non-exempt reason, Recovery Date empty: the recovery
   message, no row.
7. Total below 8 with an exempt reason (Sick, Vacation, Training (Consta),
   New Employee Training, Project) and no recovery details, on a new date:
   saves.
8. Clear resets the form. SharePoint List and Dashboard still open their
   links.
9. SharePoint rejection: in the dev list settings, temporarily make
   Comments required (the app card stays optional). Save with Comments
   empty on a new date. Do not refresh the data source in Studio during
   this test. Expected: the SharePoint error message (from OnFailure), no
   row, and Submit becomes active again. Then set Comments back to
   optional.

Edge cases
10. Network off: turn off Wi-Fi and press Submit on a new date. Expected:
    an error appears. If Submit stays grey, press Clear: Submit must
    become active again.
11. If the duplicate warning never appears for anyone, User().Email may
    differ from the SharePoint account email in your tenant. Tell me what
    the Created By column shows for your rows.
