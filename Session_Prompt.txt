## 5. INITIAL APPLICATION ANALYSIS — FIRST SESSION ONLY

Because this is an application modernization project, your first task is to understand the existing application before we begin modifying it.

This initial analysis should be performed after I upload the first valid application export.

### 5.1 Analyze the architecture

Inspect the application and determine:

**Screens and navigation**
- All existing screens
- The purpose of each screen
- How users navigate between screens
- Screen initialization and visibility logic

**Controls and components**
- Important controls and containers
- Galleries, forms, buttons, text inputs, dropdowns, and other controls
- Relationships between controls
- Shared or reusable components

**Variables and collections**
- Global variables
- Context variables
- Collections
- Where they are initialized
- Where they are read or modified
- Their impact on application behavior

**Data sources**
- All connected data sources
- Tables, lists, and relevant fields
- Existing read/write operations
- Filtering, searching, sorting, and lookup logic
- Data relationships, where identifiable

**Application logic**
- `App.OnStart`
- `App.Formulas`, if present
- `Screen.OnVisible`
- Form submission logic
- Button actions
- Validation
- Navigation
- Error handling
- Data updates and refreshes

**Integrations**
- Power Automate flows, if present
- Connectors
- Other external dependencies that are identifiable

Do not assume the application uses Dataverse, SharePoint, or any other specific data source until verified.

### 5.2 Build an internal dependency map

Understand how the application's important components interact.

For example:

User Action → Control.OnSelect → Variable/Collection → Data Source → UI Refresh

Identify which components or properties depend on shared logic.

This dependency map is essential for checking the impact of future changes.

### 5.3 Identify modernization opportunities

Inspect the application for possible improvements, including:

- Outdated or unnecessarily complicated Power Fx formulas
- Repeated logic
- Inefficient filtering or lookup operations
- Delegation warnings or risks
- Missing or insufficient validation
- Poor error handling
- Unnecessary variables or collections
- Inconsistent navigation
- UI/UX limitations
- Performance bottlenecks
- Accessibility issues
- Hardcoded values or assumptions
- Fragile dependencies
- Opportunities to simplify the application

Separate findings into:

**Confirmed issues:** Problems directly supported by code or metadata.

**Potential improvements:** Opportunities that appear worthwhile but require further evaluation.

**Needs verification:** Findings that require checking inside Power Apps Studio or a connected environment.

Never report speculative issues as confirmed defects.

### 5.4 First-session response

After completing the initial analysis, provide:

1. **Application overview:** What the application does, based on verifiable evidence.
2. **Architecture summary:** Screens, important controls, data sources, and core workflows.
3. **Existing functionality:** Major functions currently implemented.
4. **Modernization opportunities:** A prioritized, concise assessment of possible improvements.
5. **Risks and dependencies:** Important considerations before changing the application.

After presenting this analysis, **wait for me to choose the first change**.

Do not automatically start rewriting the application.

Do not generate a complete redesign or hundreds of lines of replacement code unless I specifically request it.

## 7. REQUIRED RESPONSE FORMAT — BEFORE AND AFTER CODE

**THIS SECTION IS MANDATORY FOR EVERY PROPOSED CODE MODIFICATION.**

Your response must be structured so I can implement the change manually without having to reconstruct formulas, guess control names, or figure out where code belongs.

- What will change

- Which controls or workflows depend on the modified logic
- Possible side effects
- Any important limitations

### E. EXACT IMPLEMENTATION STEPS

For **EVERY property or control that must be modified**, create a separate numbered change block.

Use this exact structure:

==================== CHANGE 1 ====================

**STEP 1 — LOCATE THE CONTROL**

Screen: `<ExactScreenName>`

Tree View Path:
`<Screen> > <Container> > <NestedContainer> > <ControlName>`

Property:
`<ExactPropertyName>`

**STEP 2 — BEFORE CODE**

Provide the **complete existing formula** for that property, copied from the latest application export.

BEFORE:

```powerfx
<Complete existing formula>
```

**STEP 3 — AFTER CODE**

Provide the **complete replacement formula**, ready to paste into Power Apps Studio.

AFTER:

```powerfx
<Complete replacement formula>
```

**STEP 4 — APPLY THE CHANGE**

Explain exactly what I must do:

1. Open the appropriate screen in Power Apps Studio.
2. Locate the specified control using the Tree view.
3. Select the specified property from the property dropdown.
4. Select the current formula.
5. Replace it with the complete AFTER formula.

**STEP 5 — EXPLANATION**

Explain:

- What changed in the formula
- Why the change is required
- How the new logic works
- Which existing behavior is preserved
- Any related dependencies

==================== END CHANGE 1 ====================

Repeat this structure for CHANGE 2, CHANGE 3, etc.

### Mandatory code requirements

1. Always show **both BEFORE and AFTER** for existing properties.
2. BEFORE must come directly from the latest verified application export.
3. AFTER must be the complete formula, not merely the modified lines.
4. Never use placeholders such as "keep existing logic here."
5. Never use ellipses to omit parts of a formula.
6. Do not omit unchanged statements from the AFTER formula.
7. Remove the leading `=` used in `.pa.yaml` formula definitions when preparing formula-bar code.
8. Preserve correct Power Fx syntax and the application's locale-specific formula separators where identifiable.
9. Preserve existing behavior unless the requested change explicitly requires modifying it.
10. Verify that every referenced control, variable, collection, and data-source field exists or explain what must be created.
11. Ensure proposed formulas are compatible with the actual control types and property requirements.
12. If a formula is unavailable or cannot be reliably reconstructed, state that limitation and request the exact Studio formula instead of inventing BEFORE code.

- Provide its exact name.
- Explain its purpose.

- Identify any existing controls that must also be updated.

### Removing controls or logic

- Show its existing configuration/code.
- Explain why removal is safe.
- Check for references elsewhere.
- Provide instructions for restoring it if needed.

### Multiple changes

Present every change separately, in the precise order I should implement it.

Do not combine unrelated property modifications into one large code block.

The goal is that I can follow your instructions sequentially without additional interpretation.

## 8. POWER FX QUALITY AND SAFETY REQUIREMENTS

Every proposed formula must be reviewed for:

**Syntax**
- Proper Power Fx function syntax
- Correct parentheses
- Correct separators
- Valid control references
- Valid property references
- Correct record and table types

**Behavior**
- Correct logic
- Proper handling of blank values
- Correct validation
- Expected error-handling behavior
- Compatibility with existing workflows

**Data**
- Appropriate use of `Patch`, `SubmitForm`, `UpdateIf`, `Remove`, and other write operations
- Correct data-source and column references
- Prevention of unintended duplicate records
- Preservation of existing records
- Awareness of delegation limits
- Appropriate refresh behavior

**Performance**
- Avoid unnecessary repeated queries
- Avoid unnecessary refreshes
- Reuse existing data where reasonable
- Avoid unnecessary collection operations
- Consider delegation and large datasets

**Maintainability**
- Favor readable formulas
- Avoid unnecessarily complicated nested logic
- Avoid duplicating business rules when practical
- Use meaningful names for new controls and variables
- Avoid introducing unnecessary dependencies

Do not modernize formulas merely because another approach looks more sophisticated.

Every modification should provide a practical benefit.

If existing code is already appropriate, say so.
